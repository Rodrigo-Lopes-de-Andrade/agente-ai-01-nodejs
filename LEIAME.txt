2. INSTALAR O uv
--------------------------------------------------------------------------------

  O uv substitui o conda. A diferenca pratica: o conda instala um Python
  gigante compartilhado por todos os projetos; o uv cria uma pasta .venv
  DENTRO do capitulo, com as versoes exatas que ele precisa. Nada vaza de um
  projeto para o outro -- e ele e muito mais rapido.

  Linux, WSL ou macOS:

      curl -LsSf https://astral.sh/uv/install.sh | sh
      source $HOME/.local/bin/env

  Windows (PowerShell):

      powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

  Conferir:

      uv --version


--------------------------------------------------------------------------------
3. CRIAR O AMBIENTE DO CAPITULO
--------------------------------------------------------------------------------

      cd ~/projects/dsa/12-Projeto
      uv sync

  So isso. O uv le o pyproject.toml, baixa o Python 3.12 se necessario, cria a
  pasta .venv e instala tudo. Ele tambem gera o uv.lock, que guarda a versao
  exata de cada pacote instalado -- e o que garante que o ambiente possa ser
  recriado identico depois.

  Observacao sobre as versoes: no pyproject.toml elas usam ">=" e nao "==".
  Travar tudo com "==" e como tirar uma foto: no dia seguinte ja envelheceu --
  foi exatamente o que aconteceu com o requirements.txt original. O ">=" diz
  "desta versao para cima" e quem guarda a foto exata e o uv.lock.

  O requirements.txt original continua na pasta, como registro historico do
  que o curso usava em fevereiro de 2025. Ele nao e mais usado.

4. INSTALAR O LLM LOCAL (OLLAMA) -- OPCIONAL, MAS RECOMENDADO
--------------------------------------------------------------------------------

  O capitulo usa a Groq, que e nuvem e exige chave de API. O Ollama roda na
  sua propria maquina: sem chave, sem custo, sem internet. E a rede de
  seguranca -- se voce nao tiver nenhuma chave, o app continua funcionando.

  PASSO 1 (o que derruba muita gente no WSL):

      sudo apt-get update && sudo apt-get install -y zstd

  O instalador do Ollama descompacta os arquivos com zstd. Sem ele, a
  instalacao morre com:

      ERROR: This version requires zstd for extraction

  PASSO 2 - instalar:

      curl -fsSL https://ollama.com/install.sh | sh

  No Windows, baixe em https://ollama.com/download

  PASSO 3 - baixar o modelo:

      ollama pull llama3.2

  PASSO 4 - conferir:

      ollama list

  SOBRE O SERVIDOR: se o systemd estiver ativo (o comando 'ps -p 1 -o comm='
  responde "systemd", que e o caso da maioria dos WSL modernos), o instalador
  registra o Ollama como servico e ele sobe sozinho. Voce NAO precisa rodar
  'ollama serve'. Se nao houver systemd, rode 'ollama serve' em outro terminal
  e deixe aberto.

  PEGADINHA DO WSL2: se voce instalou o Ollama no WINDOWS e nao no Linux, ele
  nao esta em localhost do ponto de vista do WSL. O endereco e o IP que
  aparece no nameserver do /etc/resolv.conf:

      grep nameserver /etc/resolv.conf

  Coloque esse IP no .env:

      OLLAMA_HOST=http://SEU.IP.AQUI:11434

  A celula 1.6 do notebook detecta os dois casos sozinha.

6. CHAVES DE API (.env)
--------------------------------------------------------------------------------

  O arquivo .env fica na pasta do capitulo e guarda as chaves. Ele ja esta
  protegido pelo .gitignore -- nao vai junto se voce enviar o projeto ao
  GitHub.

  AVISO: uma chave de API e uma SENHA QUE GASTA DINHEIRO. Quem tiver a sua
  chave faz chamadas na sua conta e voce recebe a fatura. Nunca poste em
  print, video, GitHub ou grupo de WhatsApp. Se desconfiar que vazou, revogue
  no painel do provedor e gere outra -- revogar e gratuito.

  Onde pegar cada chave:

      Groq       https://console.groq.com/keys
      OpenAI     https://platform.openai.com/api-keys
      Anthropic  https://console.anthropic.com/settings/keys
      Grok (xAI) https://console.x.ai/
      Ollama     nao precisa de chave (roda local)

  COMO O APP ESCOLHE O PROVEDOR, passo a passo:

  1) Ao abrir, o app le o .env e monta uma lista so com os provedores cuja
     chave esta preenchida DE VERDADE. Chave ausente, apagada ou ainda com o
     texto de exemplo ("cole-sua-chave") conta como nao configurada: o
     provedor simplesmente nao entra na lista, sem erro.
  2) A ordem da lista e Groq > OpenAI > Anthropic > Grok, e o Ollama local
     entra por ultimo (ele nao precisa de chave) -- mas so se houver um
     servidor Ollama respondendo. Sem chave nenhuma e sem Ollama, o app
     avisa "Nenhum motor de IA disponivel" e para.
  3) Na barra lateral, logo abaixo das instrucoes, a caixa "Escolha o LLM"
     mostra essa lista. O primeiro item e o padrao; para usar outro, basta
     escolher na caixa -- nao precisa mexer no .env nem reiniciar.
  4) Abaixo da caixa, uma mensagem confirma o provedor e o modelo em uso.
     O nome do modelo vem da variavel *_MODEL do provedor no .env (ex.:
     GROQ_MODEL); se ela estiver vazia, o app usa um modelo padrao.

  Quer que um provedor apareca na caixa? Preencha a chave dele no .env e
  reinicie o app (Ctrl+C no terminal e 'uv run streamlit run dsa_app.py'
  de novo): o .env e lido na partida.

  Se der erro 404 de modelo, veja os nomes validos da SUA conta:

      uv run python dsa_lista_modelos.py

  PASSO ORIGINAL (aula)         | PASSO MODERNO (2026)
  ------------------------------|-----------------------------------------------
  Conta gratuita AWS            | Igual, mas o free tier mudou (9.1)
  EC2 t2.micro, Amazon Linux 2  | t4g.micro (ARM) ou t3.micro, Ubuntu 24.04 LTS
  SSH com arquivo .pem          | EC2 Instance Connect (botao "Conectar")

  Criar pasta app e copiar      | git clone do seu repositorio
  pip install -r requirements   | uv sync

  http://IP:8501                | idem, ou Caddy com HTTPS na porta 443
  Desligar pela console         | aws ec2 stop-instances (ou terminate)

  9.1 A CONTA E O FREE TIER

  Em julho de 2025 a AWS trocou o modelo de conta gratuita. Antes: 12 meses
  de t2.micro gratis (750 h/mes). Agora: conta nova recebe CREDITOS (ate
  US$ 200, validos por 6 meses) e escolhe entre o plano "Free" (nao cobra
  nada; a conta e encerrada quando os creditos acabam ou os 6 meses passam)
  e o plano "Paid" (cobra o que passar dos creditos). A EC2 consome credito
  desde a primeira hora ligada.

  Se escolher o plano Paid, ou se a sua conta e anterior a julho de 2025,
  faca isto no primeiro dia, antes de criar qualquer instancia:

      Console AWS > Billing > Budgets > Create budget > US$ 1,00 > seu e-mail

  E um alarme: se a fatura passar de 1 dolar, voce recebe e-mail. Nao custa
  nada e evita a historia classica da instancia esquecida ligada por um mes.

  9.2 A INSTANCIA

  No console: EC2 > Launch instance.

      Nome            dsa-daytrade
      Imagem (AMI)    Ubuntu Server 24.04 LTS
      Arquitetura     64-bit (Arm)               <-- habilita a familia t4g
      Tipo            t4g.micro (2 vCPU, 1 GB)   ou t3.micro se preferir x86
      Par de chaves   "Proceed without a key pair" (usaremos Instance Connect)
      Rede            deixe "Allow SSH" marcado; marque "Allow HTTPS" e
                      "Allow HTTP" (portas 22, 443 e 80)
      Disco           8 GB gp3 (o padrao basta)

  Por que ARM: a familia t4g (processador Graviton) custa ~20% menos que a t3
  equivalente, e o uv.lock deste projeto resolve nas duas arquiteturas sem
  mudar nada -- todos os pacotes (pandas, numpy, pyarrow, lxml...) tem wheel
  para aarch64.

  Por que 1 GB e apertado: pandas + plotly + phidata + streamlit ocupam uns
  400-500 MB em repouso. Sobra pouco para o pico de uma analise. A solucao e
  criar um arquivo de swap (9.4), que da folga sem custar nada.

  9.3 CONECTAR (sem .pem)

  Selecione a instancia > botao "Conectar" > aba "EC2 Instance Connect" >
  "Conectar". Abre um terminal dentro do navegador, ja logado como 'ubuntu'.

  Nao precisa baixar chave, nao precisa de 'chmod 400', nao tem .pem para
  perder: o Instance Connect injeta uma chave temporaria que vale 60
  segundos. A porta 22 continua aberta, mas sem chave permanente nao ha o
  que vazar. Quem quiser zero portas abertas usa o SSM Session Manager
  (exige uma IAM role com AmazonSSMManagedInstanceCore na instancia).

  Se preferir o SSH classico (ssh -i chave.pem ubuntu@IP), continua
  funcionando: crie o par de chaves no lancamento e, no Security Group,
  troque a origem da porta 22 de "Anywhere" para "My IP".

  9.4 PREPARAR A MAQUINA (substitui o Miniconda)

      # swap de 2 GB: folga de memoria para a instancia de 1 GB
      sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
      sudo mkswap /swapfile && sudo swapon /swapfile
      echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

      # uv: o mesmo instalador da secao 2, na mesma linha

      source $HOME/.local/bin/env

  Compare com o original: 'wget Miniconda3-latest-Linux-x86_64.sh' baixava
  ~100 MB, rodava um instalador interativo e criava um Python compartilhado.
  O uv tem ~20 MB, instala em 2 segundos e baixa o Python 3.12 sozinho no
  primeiro 'uv sync'. E o instalador e identico ao que voce usou no WSL.

  9.5 TRAZER O CODIGO E AS CHAVES (substitui "crie a pasta app e copie")

      git clone https://github.com/Rodrigo-Lopes-de-Andrade/agente-ai-01.git ~/app
      cd ~/app
      nano .env            # cole as chaves, igual ao seu .env local
      chmod 600 .env       # so o dono le

  O .env NAO esta no repositorio (o .gitignore o exclui, de proposito): chave
  de API em repositorio publico e roubada por robo em minutos. Voce cria o
  arquivo na instancia, na mao, uma unica vez. O conteudo e o mesmo da
  secao 6.

  O projeto ja esta no GitHub (repositorio acima). Sem git, a alternativa
  seria copiar do WSL com scp ou rsync -- mas ai a cada alteracao voce copia
  de novo. Com git, a atualizacao na instancia e 'git pull'.

  9.6 INSTALAR AS DEPENDENCIAS (substitui pip install -r requirements.txt)

      uv sync --no-dev

  Um comando. O uv le o pyproject.toml, baixa o Python 3.12, cria a .venv e
  instala as versoes exatas do uv.lock -- as mesmas que funcionam na sua
  maquina. Demora 1-2 minutos na t4g.micro.

  O '--no-dev' pula o grupo [dependency-groups] dev do pyproject.toml, onde
  ficam jupyter, ipykernel e ipywidgets: ferramentas de estudo que o servidor
  nunca abriria (~200 MB). No WSL voce roda 'uv sync' sem a flag e o grupo
  entra normalmente -- por isso o notebook continua funcionando la.

  9.7 SUBIR O APP COMO SERVICO (substitui nohup ... &)

  O 'nohup ... &' da aula funciona ate o primeiro reboot ou o primeiro
  travamento: depois disso o app fica fora do ar ate alguem entrar e subir de
  novo. Um servico systemd resolve os dois casos -- e e o jeito padrao de
  rodar qualquer programa "para sempre" em Linux.

      sudo tee /etc/systemd/system/dsa-app.service > /dev/null <<'EOF'
      [Unit]
      Description=DSA Day Trade Analytics (Streamlit)
      After=network-online.target
      Wants=network-online.target

      [Service]
      User=ubuntu
      WorkingDirectory=/home/ubuntu/app
      ExecStart=/home/ubuntu/.local/bin/uv run streamlit run dsa_app.py \
          --server.port=8501 --server.address=0.0.0.0 --server.headless=true
      Restart=always
      RestartSec=5

      [Install]
      WantedBy=multi-user.target
      EOF

      sudo systemctl daemon-reload
      sudo systemctl enable --now dsa-app     # liga agora E no boot
      sudo systemctl status dsa-app           # espere "active (running)"

  Comandos do dia a dia:

      journalctl -u dsa-app -f                # logs ao vivo (Ctrl+C sai)
      sudo systemctl restart dsa-app          # depois de um git pull
      sudo systemctl stop dsa-app             # para sem desligar a maquina

  Tres detalhes do arquivo acima:

  - ExecStart usa o caminho completo do uv. Servicos nao leem o seu .bashrc,
    entao 'uv' sozinho daria "command not found".
  - --server.headless=true impede o Streamlit de tentar abrir um navegador
    (nao existe navegador no servidor) e de perguntar o e-mail na primeira
    execucao, o que travaria o servico esperando resposta.
  - O .env e lido pelo load_dotenv() do dsa_app.py, que ja aponta para a
    pasta do proprio script (secao 1, quebra 3). Nada a configurar.

  9.8 ABRIR PARA O NAVEGADOR

  Opcao A -- direto na porta 8501 (igual a aula)

      Console > EC2 > Instancia > aba "Security" > Security group >
      Edit inbound rules > Add rule:
          Type: Custom TCP   Port: 8501   Source: My IP

  Acesse http://IP_PUBLICO:8501. "My IP" em vez de "Anywhere" e de proposito:
  so voce enxerga o app enquanto testa.

  Opcao B -- HTTPS com Caddy (para mostrar a cliente)

  Um endereco https://... com cadeado passa mais confianca que um IP com
  porta. O Caddy e um servidor web que fica na frente do Streamlit, emite o
  certificado sozinho (Let's Encrypt) e renova sem voce lembrar.

  Precisa de um nome de dominio apontando para o IP. O DuckDNS da um gratis:
  crie uma conta em duckdns.org, escolha um nome (ex.: dsa-daytrade) e cole o
  IP publico da instancia.

      sudo apt-get install -y caddy
      echo 'dsa-daytrade.duckdns.org {
          reverse_proxy localhost:8501
      }' | sudo tee /etc/caddy/Caddyfile
      sudo systemctl reload caddy

  No Security Group: 80 e 443 abertas para "Anywhere" (ja estao, se marcou
  as caixas no lancamento); a 8501 NAO precisa estar aberta, o Caddy fala
  com ela por dentro da maquina. Acesse https://dsa-daytrade.duckdns.org.

  O Streamlit usa WebSocket para atualizar a tela. Com Nginx isso exige tres
  linhas de configuracao que todo mundo esquece; o Caddy repassa WebSocket
  sem configurar nada -- e por isso a escolha aqui.

  9.11 DESLIGAR AO TERMINAR

  Pela console: EC2 > Instancia > Instance state > Stop (ou Terminate).

  Pela linha de comando, se tiver o AWS CLI configurado no WSL:

      aws ec2 stop-instances --instance-ids i-0123456789abcdef0
      aws ec2 terminate-instances --instance-ids i-0123456789abcdef0

  STOP pausa: a CPU deixa de cobrar, mas o disco (8 GB, centavos) e o IP
  continuam. Volta exatamente como estava. TERMINATE apaga a maquina e o
  disco: custo zero, mas refaz-se tudo de 9.2 em diante (com git clone e
  systemd, isso leva 10 minutos).

  Para nao depender da memoria: EC2 > Instancia > aba "Monitoring" > Create
  alarm > acao "Stop this instance" quando CPU < 5% por 2 horas. A propria
  AWS desliga a maquina esquecida.

  9.12 E SE PULAR A EC2?

  O curso usa EC2 porque ensinar AWS e parte do objetivo. Para o app em si,
  existe caminho com menos manutencao:

  - STREAMLIT COMMUNITY CLOUD (share.streamlit.io): gratis, faz deploy
    direto do repositorio GitHub, HTTPS pronto, gerenciador de secrets para
    as chaves de API. Le o uv.lock. Zero servidor para cuidar. Limite:
    recursos modestos e o app "dorme" apos alguns dias sem acesso. E o
    caminho da SECAO 10, passo a passo.

  - CONTAINER (AWS App Runner, Lightsail Containers, Fly.io): um Dockerfile
    de 10 linhas com uv, e o provedor cuida de HTTPS, reinicio e escala.
    Custa um pouco mais que a EC2 crua, cobra menos em horas suas.

  A EC2 continua sendo a escolha certa para APRENDER como as pecas se
  encaixam -- o que e exatamente o que esta secao fez.

  Nao existe API nem linha de comando para a primeira publicacao: ela e

  10.1 POR QUE NAO A VERCEL (OU OUTRA PLATAFORMA SERVERLESS)

  A pergunta e natural: a Vercel e a plataforma de deploy mais conhecida e,
  desde julho de 2026, aceita ate WebSocket em funcoes Python. Mesmo assim o
  Streamlit nao roda la, por tres motivos -- e cada um sozinho ja basta:

  1) A Vercel executa apps ASGI/WSGI (FastAPI, Flask, Django): um objeto
     'app' que ela chama a cada requisicao. O Streamlit e um servidor
     completo (Tornado) que abre a porta 8501 e serve HTML, WebSocket e
     arquivos estaticos ele mesmo. Nao existe adaptador; nao ha como
     "exportar" o Streamlit como funcao.
  2) Uma funcao serverless nasce, responde e morre. O Streamlit guarda a
     sessao do usuario (ticker digitado, resultado da analise) na memoria
     do processo. Quando a funcao expira, a conexao cai, e a reconexao pode
     chegar em outra instancia, que nao sabe de nada: a tela reseta ou
     trava em "Please wait...".
  3) Funcoes Python da Vercel tem limite de 250 MB descompactados. pyarrow
     + pandas + numpy + plotly + lxml + phidata passam disso com folga.

  Resumindo: serverless e o oposto do que o Streamlit precisa, que e um
  processo vivo enquanto o usuario estiver com a pagina aberta. Plataformas
  que mantem esse processo: Streamlit Community Cloud (esta secao), Hugging
  Face Spaces, Render, Railway, Fly.io -- ou uma EC2 (secao 9).

  Caberia na Vercel um app REESCRITO: backend FastAPI (reaproveitando
  dsa_extrai_dados, os graficos Plotly como JSON e os tres agentes) e um
  frontend em Next.js ou HTML. E outro projeto, que abandona o Streamlit --
  justamente a ferramenta que o capitulo ensina.

  10.4 SECRETS: AS CHAVES NA NUVEM

  Na sua maquina as chaves vivem no .env. Na nuvem nao existe .env -- e nem
  poderia: ele nao vai para o GitHub. O Community Cloud tem um painel
  proprio de Secrets, em formato TOML (chave = "valor", uma por linha). Cole
  ali o mesmo conteudo do seu .env, com ASPAS nos valores:

        GROQ_API_KEY = "gsk_..."
        GROQ_MODEL = "openai/gpt-oss-120b"
        OPENAI_API_KEY = "sk-..."
        OPENAI_MODEL = "gpt-4o-mini"

  Por que o app nao precisou mudar: o Streamlit expoe os secrets de nivel
  raiz TAMBEM como variaveis de ambiente, na partida do servidor. O
  os.getenv("GROQ_API_KEY") do dsa_app.py encontra a chave do mesmo jeito
  que encontrava a do .env. Nao use secoes ([grupo]) no TOML: so o nivel
  raiz vira variavel de ambiente.

  Para mudar uma chave depois: painel do app em share.streamlit.io > menu
  "..." > Settings > Secrets. O app reinicia sozinho.

  Nao coloque OLLAMA_HOST nos secrets: nao ha Ollama na nuvem, e o app ja
  esconde a opcao quando nao encontra o servidor.

  10.5 ATUALIZAR O APP DEPOIS

  Todo push no branch main republica o app em cerca de um minuto:

        git add -A
        git commit -m "descricao da mudanca"
        git push

  Se mudar dependencias ('uv add ...'), o uv.lock muda junto e vai no mesmo
  commit; o Community Cloud reinstala.

  Para reconstruir sem mudar codigo: painel do app > "..." > Reboot app.
  Para apagar: "..." > Delete app.

  10.6 LIMITES DO PLANO GRATUITO

  - Recursos modestos (RAM e CPU compartilhados). O app cabe, e uma analise
    leva os mesmos 30-90 segundos que leva na sua maquina: o tempo e do
    LLM, nao do servidor.
  - O app "dorme" depois de alguns dias sem ninguem abrir. A visita seguinte
    demora cerca de um minuto para acorda-lo. Nada se perde.
  - Repositorio publico: qualquer pessoa ve o codigo (as chaves nao: elas
    ficam nos secrets). Repositorio privado tambem funciona, mas o plano
    gratuito permite um unico app privado.
  - Nao ha Ollama nem GPU: um provedor em nuvem (Groq, OpenAI...) e
    obrigatorio.
